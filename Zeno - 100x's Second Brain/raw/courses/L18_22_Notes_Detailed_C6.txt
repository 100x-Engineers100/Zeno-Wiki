100xEngineers | 14 Mar 2026 | Instructor: Tejas
================================================================

FRAMING
Tejas called this "customizing LLM behavior" not just "fine-tuning" because fine-tuning is one lever among five — and almost always the wrong first move.

Five levers in order:
1. Prompting
2. Better context (structured inputs, richer brief)
3. RAG — fetch external/real-time data into context
4. Workflow design — break the task into sub-steps
5. Fine-tuning — last resort

Live example he walked through: MacBook Neo 20-30 second ad script.
- Raw vague prompt → generic output, no product features mentioned
- Structured prompt (features, tone, CTA, audience) → better, closer
- Add RAG for real-time pricing/claims → grounded facts
- Break into hook → body → CTA workflow → reliable structure
- STILL inconsistent? → NOW consider fine-tuning

"Fine-tuning teaches the model to reproduce repeated behavior more reliably, from examples you showed it. That is what fine-tuning does."

When fine-tuning is the right answer:
- Outputs vary 2-out-of-5 times despite good prompting + workflow
- You want consistent JSON output schema
- Narrow, specific task where the pattern is clear
- Long prompts you want to eliminate (reduces token cost at inference)
- Running a smaller, cheaper model for one specific job

When it's the WRONG answer:
- You need real-time / external data → that's RAG, not fine-tuning
- Instructions are unclear → clean up your task definition first
- Dataset is small or low quality → "if you don't have high-quality data to study for an exam, you're not going to pass"
- RAG vs fine-tuning confusion: Tejas explicitly said these are not comparable. RAG fetches external facts into the prompt at inference time. Fine-tuning changes weights permanently. "Don't fine-tune to compensate for missing knowledge — that's a RAG opportunity."

---

COST MODEL (what Tejas showed on slides)
Before fine-tuning: GPT-5.4, say 900 prompt tokens + 600 output tokens. Expensive, long prompts.
After fine-tuning smaller model: prompt tokens drop because model already learned the behavior. Output tokens also drop — no extra filler. "My model has learned that behavior, so the cost goes down quite a bit."

Strategy: fine-tune a smaller model → cheaper to run, faster inference (tokens/sec goes up), one-time training cost amortizes over many calls.

---

LLM TRAINING LIFECYCLE — 3 STAGES

Stage 1: Pre-training
"The big companies take a massive dataset — think internet by 10 — terabytes or more. They train on it using two approaches: masked language modeling (predict hidden tokens within a sequence) or causal language modeling (predict next token given preceding context). The model learns to be a next-token predictor. That's all a base model does. But it has a ton of knowledge because of how much data went in."
Cost: thousands of GPUs (H100s), months of compute, millions of dollars. "This $10M could be $2-5M today with more efficient methods."
Output: base model — a next-token predictor, nothing more.

Stage 2: Supervised Fine-tuning (SFT)
Take the base model, train on labeled instruction-input-output pairs for a specific task. This is what we do.
"You initialize the model, the weights are registered, parameters are registered, the model starts learning." Far cheaper — "maybe 10 H100s" vs thousands.
Transfer learning: "pick the base model that already comes closest to what you want. If Llama's latest is closest to your writing style, use that. It's already learned patterns you can build on."
Base model selection: "try KimiK 2.5, try a DeepSeek model, try Llama — whichever comes closest to your expected output, use that to fine-tune."

Stage 3: Preference Alignment (RLHF / DPO)
"You've used ChatGPT — one in 10-20 prompts it gives you two answers and asks you to choose. That's them getting preference data."
RLHF: human picks answer A or B → that preference data trains a smaller reward model → reward model scores future LLM outputs → LLM learns from those scores.
DPO (Direct Preference Optimization): "Stanford found you don't need the separate reward model. You feed the prompt + chosen answer + rejected answer directly back to the LLM for fine-tuning."
"Your single thumbs-up doesn't change the model. But if 100 users select the same pattern, that's enough signal for the next version."
Done by big labs only — requires massive human feedback data.

---

THREE SFT TECHNIQUES

Full Fine-tuning:
"You update ALL parameters — the floating point numbers that make up the model. It goes through the entire LLM and refreshes how it thinks. Best performance. But requires a lot of computational resources and high VRAM."
Risk: catastrophic forgetting. "If your training data has even a few bad samples, you can teach it something wrong across the entire model. A model that knew how to write essays can become bad at writing entirely."

LoRA (Low-Rank Adaptation):
"You don't update all the weights. You take a chunk of the weights — a small percentage — and train only those. You get a detachable adapter layer on top of the base model."
How inference works: "when you prompt the fine-tuned model, it asks both the base layer and the LoRA layer for the output. They combine and give one single answer. It's an adapter."
Portability: "You train a LoRA on Llama 3. Llama 3.1 releases. Because they share the same architecture, you can take that LoRA file and place it on top of 3.1."
"LoRA trainable parameters = ~2% of total. That's what parameter efficient means."
Performance vs full fine-tune: "spend 10% of the cost, get 95% of the outcome for narrow tasks."

QLoRA:
"Same as LoRA but reduces the precision of the floating point numbers. Weights are normally 32-bit or 16-bit floats. QLoRA drops to 4-bit — roughly 1/4 of the GPU memory needed."
"Originally sold as: train 7B, 20B LLMs on a single GPU. Even a 30B or 70B on one A100 or H100."
Trade-off: "slight performance drop on complex tasks. On simple tasks, LoRA and QLoRA are on par."
Use when: "I need a bigger base model but LoRA for that model is too expensive on my GPU."

---

PRACTICAL GUIDANCE
"Q: which weights does LoRA select to train? A: you can't choose. The trainer selects a percentage. It's impossible to know which weights draw patterns closest to what you're training for."
"Q: what size model to fine-tune? A: 7B vs 15B — test both on your task. If there's a big leap in base quality, go with 15B. If they're close, go 7B — cheaper to run and train."
"Smaller model = trained on less data = weaker general language understanding. If the foundation is bad, fine-tuning won't save it."
MRI/X-ray cancer detection models: "those are not LLMs — different type of neural network. But yes, fine-tuned on cancer image data to close the gap from 30% miss rate to 5-10%."

LECTURE 19 — DATA PREPARATION FOR FINE-TUNING
100xEngineers | 20 Mar 2026 | Instructor: Tejas
================================================================

"Data is probably the single biggest thing in fine-tuning. If you don't have the data, fine-tuning isn't even a question."

SUPERVISED vs UNSUPERVISED
Pre-training is self-supervised/unsupervised: "just raw data fed into a neural network. It finds patterns on its own. No labels."
Fine-tuning is supervised: "for THIS input, THIS is the ideal output. I'm labeling it. That's one training sample."

WHAT "GOOD DATA" ACTUALLY MEANS

Raw material ≠ training data. Example he used:
- Raw: "AI video editor. Fast exports. Autocaptions. For creators. Tone: punchy."
- Weak training sample: "Write something about this tool" → output was vague
- Strong training sample: "Write a 25-30 second Instagram Reel script for creators. Must mention fast exports and autocaptions. Tone: punchy, creator-native. Avoid corporate language." → output followed the structure

"The task has to be clearer. Context has to be well put together. Constraints have to be explicit."

FOUR PILLARS

Accuracy: "if you feed wrong information, LLM learns that. If you wrote 'Q2 revenue up 50%' but it was 5%, it learns 50%. Or if your output example says 'punchy' but it's actually educational in tone — it learns that wrong pattern."

Diversity + Consistency explained together (student asked if they contradict):
"Diversity = across groups. If 80/100 samples are the same style, the model only learns that style. You need even distribution across tones, audiences, formats.
Consistency = inside a group. If 10 punchy-script samples all have different structure, the model gets mixed signals. Within a style, structure must be consistent."

Complexity: "if you only train on 25-second scripts, it won't handle 2-minute scripts. Real-world users will give harder inputs. Train on those too."

---

5-STEP DATA RECIPE

Step 1 — Collect: "gather from real sources. Tag each sample: topic, style, audience, complexity. Even at 5 samples it seems trivial. At 500, without tags, you lose track."
Common mistake: "collecting data that's domain-related but not task-related."

Step 2 — Clean: remove PII, bad punctuation, inconsistent naming ("UGC people" vs "creators" → pick one and normalize). "Overcleaning is a small problem — don't make examples stop looking like real prompts."
Can use LLMs for bulk cleaning but manual spot-checks are necessary.

Step 3 — Deduplicate + Decontaminate:
Dedup: "near-identical entries — slight wording changes — remove them. If 5 samples talk about Google TextFX, you're teaching that pattern too hard."
Decontaminate: "split dataset 70-80% training, 20-30% eval. Do NOT put near-duplicate samples in both. If the eval set looks like training data, your eval scores are meaningless — model memorized the answer, not learned the pattern."
"It's like asking a student a question they literally studied. Does that mean they understand the concept?"

Step 4 — Annotate (hardest step): convert cleaned samples into JSON instruction-input-output format.

JSON structure (he showed this directly):
```json
{
  "instruction": "Write a 25-second Instagram Reel script for creators",
  "input": "Product: AI video editor. Features: fast exports, autocaptions. Tone: punchy. Avoid: corporate language.",
  "output": "Editing used to take forever... [full script]"
}
```
"Input field is optional. Instruction must exist. Output must exist."
"Instruction = what to do. Input = context/constraints. Output = ideal answer."

Conversational format for chatbot behavior:
```json
{"role": "system", "content": "..."},
{"role": "user", "content": "..."},
{"role": "assistant", "content": "..."}
```

Reasoning/decision dataset: "instruction asks model to pick better hook from A vs B, and explain why. Output: 'Hook B stronger because it starts with a familiar pain point.'"

Step 5 — Quality review: "build a checklist. If an output says 'this revolutionary product will transform the way creators work forever' — that's hype language. Remove it or fix it. Every sample matters."

---

TOOL: Distilabel (Python)
"Takes raw data, converts into structured examples, adds small variations, generates multiple output drafts. At the end, saves as a dataset file you can directly feed into the trainer."
For no-code: Google Sheets + Gemini AI feature works for small datasets.

---

KEY Q&A
Q (Bhavin): "In-context learning (system prompt examples) vs fine-tuning — what's different under the hood?"
A: "In-context learning = you put examples in the prompt at inference time. Model reads them during that one call. Fine-tuning = you pass examples through a trainer tool that takes the LLM weights and updates them. The model has already learned from those examples before you ever prompt it. After fine-tuning, you don't need to include examples in the prompt — that's why token cost drops."

Q (Gurnoor): "Can we use Distilabel with different format types in one training run?"
A: "No. One training run = one consistent data format."

TRAINING WORKFLOW: 5 STEPS
1. Choose task + have dataset ready
2. Choose base model
3. Choose training method (LoRA / QLoRA / Full)
4. Prepare config (YAML)
5. Run training

Eval split: "usually 5-10%. 0.05 in the YAML config."
HuggingFace datasets: "Alpaca is one of the OG instruction-input-output datasets. ShareGPT Vikuna was another I used when GPT 3.5 came out. Go to Hugging Face, filter by domain — there are coding datasets, domain-specific datasets, everything."

---

BASE MODEL SELECTION

"We're talking fine-tuning sub-100 billion parameter models. Realistically 8B to 30B."
Currently good open-weight options: "Quen models, Llama models, KimiK 2.5, DeepSeek models."
"Test 2-3 base models on your task first. Pick the one that's already closest to your expected output."
Size trade-off: "7B vs 15B — if there's a big leap in base quality, go 15B. 15B is roughly double the cost to run."
"Smaller model = trained on less data = weaker general language understanding. If it has no foundation for your task, fine-tuning won't save it."
Llama commercial licensing caveat: "open weights, but if you deploy commercially with >1 million users you need a license from Meta."

---

TRAINING METHODS

LoRA: default. "Parameter efficient. ~2% of weights updated. Adapter file is portable. Use for most narrow tasks."
"10% of the cost of full fine-tuning, 95% of the outcome for narrow tasks."

QLoRA: use when LoRA on your target base model is too expensive for your GPU.
"QLORA was created for memory efficiency. Trades a small bit of performance. Performance diff vs LoRA is very small."

Full fine-tuning: "very expensive even for 1-3 billion parameter models. Only if budget is serious and task complexity demands it."

VRAM table from Llama Factory (Tejas showed this live):
- LoRA 16-bit, 7B model → 16GB VRAM minimum
- QLoRA 8-bit, 7B model → ~10GB VRAM
- "With just 4GB more than what LoRA 7B needs, you can run a 14B model with QLoRA."
Rule: "whatever the table says, plan for a bit more. Batch size, sequence length, dataset size all affect actual usage."

---

HYPERPARAMETERS (went through each in the Axolotl YAML)

Learning rate:
"Controls how aggressively the model updates its weights per step. Think of it as step size on a loss curve."
"Too small = very slow learning, might get stuck. Too large = overshoots, becomes unstable — ends up at a higher loss point instead of the minimum."
Tejas showed a graph: U-shaped loss curve. Learning rate determines how big each step is. Small steps → slow but precise. Large steps → fast but might overshoot the minimum.
Typical values: "between 1e-4 and 2e-5 range. QLoRA can handle slightly higher."

Warmup steps:
"At the start of training, you don't want the learning rate to be at full value immediately. Warmup says: ramp up slowly for the first N steps, then hit your target learning rate."
"You can see in training logs — learning rate starts low, climbs gradually, then stays flat."

Epochs:
"One epoch = one full pass through your dataset. 3-5 typically. Up to 10 for complex tasks."
"Small dataset + many epochs = overfitting risk. The model memorizes instead of generalizing."

Batch size:
"Divides your dataset into batches. You update weights after each batch."
"Bigger batch = more stable weight updates. But more VRAM."
"Rule: make batch size as large as your GPU allows before OOM errors. Start at 4, go up."

LoRA Rank (lora_r):
"Determines the size/capacity of the LoRA adapter layer. Higher rank = more parameters in that layer = more expressive but more memory."
"Don't set rank too high for a simple task. You're forcing the model to fill capacity it doesn't need — can cause overfitting."

LoRA Alpha (lora_alpha):
"Controls how much the LoRA layer influences the final output relative to the base model."
"High alpha = LoRA layer dominates. Low alpha = base model dominates, LoRA adds specialization."
"Think of it like the strength slider in Comfy — same concept."
"Typical: alpha = 2x rank is a common starting point."

Max sequence length (cutoff_len):
"Max tokens for the full instruction+input+output combined. If your samples are longer, they get truncated and the model learns a truncated version — that's a problem."
"Increasing this uses more VRAM."

Gradient accumulation:
"If your batch size is small (say 4) but you want the effect of a larger batch (say 16), gradient accumulation accumulates gradients over 4 batches before updating weights. Simulates a batch of 16 with the memory of a batch of 4."

TF32: "if you're using Ampere architecture GPUs (A100s, H100s), setting this true makes training faster and more accurate."

---

READING TRAINING LOGS

"Each log line shows: loss, learning rate, epoch."
Loss pattern to watch:
- "Loss starts low and stays flat → model thinks it already knows the answers → data is bad"
- Good pattern: "loss ramps up (model recognizes there's something to learn), then steadily comes down (weights updating, getting closer to expected output)"
- End of training: "it saves only that new LoRA adapter file to your output_dir. Not the full model — just the small adapter."

Most common error: OOM (out of memory). Lower batch size or sequence length.
If fine-tune results are bad: "almost always a data problem. Or wrong base model. Hyperparameter issues are secondary."

LECTURE 21 — EVALUATION OF LLMs
100xEngineers | 27 Mar 2026 | Instructor: Tejas
================================================================

"This is the most underrated part. Even OpenAI, Anthropic, Google are still figuring it out. Dedicated companies have started just to solve LLM evaluation."

WHY HARD

Traditional ML: "binary labels. Spam vs not spam. Cat vs dog. Accuracy is easy to compute."
Generative AI: "multiple right answers. 'This is a cat' and 'A cat is shown sitting here' are both correct. No fixed ground truth. Outputs vary in tone, detail, structure simultaneously."

"LLMs are also unpredictable. Same input → 10 different outputs. Sometimes sounds great, sometimes misses. When context gets longer in a conversation, performance drifts down."

"Testing on 2-3 good examples and calling it done is equivalent to saying your software works because it didn't crash once."

---

4 EVALUATION METHODS

1. Public Benchmarks (HLE, SWE-Bench, MMLU, CodeForce, etc.)
What they are: "standardized test datasets. Every model release flaunts them — Gemini 3.1 Pro scored 44% on Humanity's Last Exam, 80.6% on SWE-Bench."
Use for: selecting a base model. "Go to leaderboards — Hugging Face leaderboard, Chatbot Arena — filter by domain."
NOT useful for: evaluating your fine-tuned model. "Too generic. Doesn't reflect your specific task, your prompting style, your output criteria."

2. LLM-as-Judge (Auto-eval)
"Use a bigger/better LLM (GPT-5, Claude Opus) to score your fine-tuned model's outputs based on your rubric."
Known biases:
- "LLMs prefer long outputs — longer answer gets higher score even if it's worse"
- "Distillation bias: if an open-source model was trained on GPT outputs, using GPT to evaluate will prefer that model's style"
- "LLMs can't always differentiate a 4 from a 4.5"
- "Context-specific nuance: GPT won't know your specific writing style that you fine-tuned for"
Example prompt used: "You must provide values for 'evaluation' and 'total_rating' of your answer. Score each dimension 1-5."

3. Human Evaluation
"Still the gold standard. For creative tasks, judgment is still human."
Problems: "subjective, slow, expensive. One human gives 5/5 to a dramatic script, another gives 3/5. Different taste."

4. User Testing
"Real users in production-like conditions. Closest to actual use."

---

THE RUBRIC (required before any evaluation)

Tejas defined this for the script generator:
- Hook strength: does it grab attention in first 3 seconds?
- Tone fit: matches brand/style?
- Clarity: message easy to understand?
- Specificity: uses actual product details, not filler?
- Factual accuracy: no made-up claims?
- CTA quality: clear, relevant call to action?

"You score each dimension 1-5. This is your exam rubric. The tags you used in your data annotation = the dimensions you evaluate on."

---

RECOMMENDED WORKFLOW: Human-Verified LLM Eval Loop

Step 1: "Create 10-20 high-quality gold standard prompt-output pairs. Include edge cases NOT in training data."
Optional: "use an LLM to generate slight variations of those test prompts for more coverage. Human-verify them."
Step 2: "Run fine-tuned model on eval set. Collect outputs."
Step 3: "LLM-as-Judge: send outputs + rubric to GPT-5/Opus. Get dimension scores."
Step 4: "Human spot-check: subject matter expert reviews subset of LLM judge scores. Correct where biased."
Step 5: "Identify failure patterns. Model always weak on hook strength? Go back to data, add more hook examples. Retrain. Repeat."

"This loop keeps going until you're happy. It's a cycle — data → train → eval → back to data."

Tools: LLM Evaluation Harness (EleutherAI), Auto Evaluator. Both Python. Axolotl has LLM Evaluation Harness integration built in.

LECTURE 22 — CONNECTING THE DOTS: LLM MODULE RECAP
100xEngineers | 28 Mar 2026 | Instructor: Siddhant Goswami
================================================================

OPENING: REAL FINE-TUNING FAILURE

"This happened 3 years ago, GPT-3.5 era. OpenAI showcased it in a live event."
A content writing company wanted GPT-3.5 to write like their writers. They imported 140,000 Slack messages and fine-tuned on them. Spent hundreds of thousands of dollars.

First test prompt: "Write a 500-word blog post on prompt engineering."
Response: "Sure, I shall work on that in the morning."

"Why? Because they trained on Slack messages. Slack messages = casual conversation. 'I'll get to it tomorrow.' 'Can we sync later?' The model learned to respond like a coworker in Slack, not like a writer."

"What they should have done: use their blog posts as training data. The format you train on is the format you get."
Follow-up prompt: "I want you to write it now."
Response: "Okay."
"Even worse. The point: data format and data quality are everything."

---

THE MASTER FRAMEWORK

Every LLM failure traces to one of two root causes:

Context problem (uncertainty): model doesn't have the right information.
→ Solutions: prompt engineering, tool calling, RAG, memory

Behavior problem (forced response): model has the info but doesn't respond the right way.
→ Solutions: better prompting (first), then fine-tuning

"When models don't have relevant context they hallucinate. When they do have context they can still give the wrong behavior. These are two separate problems with separate solutions."

DECISION FLOWCHART (Siddhant's framework, used for 2+ years):

```
Start → In-context learning
      → Evaluate gap
      → Is it context or behavior?

Context gap, static data:
  → Improve prompt / examples in system prompt

Context gap, dynamic/real-time:
  → Tool calling (fetch from external source, augment prompt)

Context gap, too large for context window:
  → RAG (chunk, index, semantic search, retrieve)

Behavior gap:
  → Try prompting with behavior instructions first
  → Still failing? → Fine-tuning (SFT, LoRA)
```

Live example he ran: asked ChatGPT "which track should I choose in 100x Engineers cohort?"
ChatGPT answered correctly (code track vs no-code track) but gave a direct answer immediately.

"The way I actually help people make decisions — I don't give the answer in the first call. I ask Socratic questions. I make them think through it so they arrive at the answer themselves. That's a behavior change. Prompting can do this somewhat, but it forgets after the context window fills. To make this consistent and persistent, I need fine-tuning. That's a behavior optimization problem."

"That's not a context problem — the data about the tracks is there. It's how the model responds. That's where fine-tuning fits."

Context + behavior = can be combined. "In real-world solutions you often need both."

---

MCP & GENERATIVE UI UPDATE (March 25, 2026 release)

"Half the world is not even aware of this announcement."

MCP now under Linux Foundation: "Anthropic, OpenAI, Google all signed on. When three competitors agree on a standard, it becomes the standard. Like HTTP for the web."

MCP vs CLI debate: "People say MCP is overkill, just use CLI to call APIs directly. That's true for a one-off API call. But for an M×N problem — many models, many tools — MCP is the solution. You can't handle the security and scale of what I'm about to show with just CLI."

Generative UI demo (Canva integration shown):
"User says in Claude: create a deck for team retro.
Claude pulls data from Amplitude (analytics) → asks follow-up 'show me where old flow was losing people' → fetches Figma mockup → designs Canva presentation → all inside Claude's window.
User clicks Customize in the Canva UI rendered inside Claude → triggers Canva's API via MCP → changes made on Canva's server → rendered back in Claude."

"This is bidirectional. The UI rendered inside Claude is interactive — clicking it calls the real app server. Not Claude's server. Not Claude's context window. The actual Canva API."

"Canva provides their design system components to Claude — buttons, cards, layouts. Claude knows what UI elements to render from those templates."

Why this matters: "Canva didn't need to build a Claude integration the traditional way. They built an MCP server. Claude calls it. The iframe renders in Claude's chat. Secure, sandboxed, bidirectional."

"This is the Ajax moment. Before Ajax, web pages reloaded the entire page every time. After Ajax, pages became apps — dynamic, without reloads. Before generative UI in MCP, you got a text link or a document. After, you get the actual app embedded in chat, interactive."

---

ANTHROPIC'S MCP CONTEXT EFFICIENCY SOLUTIONS (advanced)

Problem: when you connect MCPs, all tool definitions load into the context window. 72,000 tokens just for tool definitions.

Solution 1 — Tool Search Tool:
"Instead of loading all tool definitions, Claude gets an index — like a RAG index of tools. When it needs a specific tool, it looks up the index and loads only that tool's definition. Same principle as page indexing in RAG."

Solution 2 — Programmatic Tool Calling:
"Claude acts as a developer, not a tool caller. User sends request → Claude writes Python code to call the APIs → code runs in execution environment → only the final result comes back to Claude's context window. Intermediate data never pollutes the context."
"Claude is just the coder. The execution environment handles all the tool calls."
"This is from the recursive language models paper. The same first-principles diagram — LLM layer, code execution layer, API layer — but rearranged so Claude generates code instead of making direct calls."

Platform agnostic: "these are concepts, not Anthropic-specific. You can do Tool Search Tool with any model — it's just better indexing. Programmatic tool calling works with any LLM that can write code."

Claude Skills mechanism (answered Bhavin's question):
"Claude compresses each skill.md into a 1-2 line schema — similar to a tool call definition. That schema goes in the context window, not the full .md file. When a relevant task is triggered, Claude calls the skill, just like it makes a tool call."
